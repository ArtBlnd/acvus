# types

## 1. Transparency

How the types of a program are decided is stated by the type-system document, [Transparency-constraint type system](../transparency-constraint-type-system.md), called the type system in these pages. It is the single source for type decision: O1 to O31 are its obligations, and a name in parentheses after it, as in (the type system, Changes), is one of its definitions or its Consequences. These pages keep what it does not state, and refer to it for the rest.

A body sees the target of a use at one of three levels (the type system, Transparency): itself, all of its own text, as Transparent; another body, a free fn, a method or a lambda, its text, separately at each use, as Semi-transparent; an extern fn or a context, its declaration, as Opaque. Types are decided where transparency changes, and the values that meet within one transparency are unified into one class (O1). A type an extern fn's declaration writes, and a context's type, which the host gives, are external: fixed outside the transparency of the position they are used at (the type system, Type states). A hole, a type parameter a declaration writes, has a free class at each use (O13), so a value passing into it is its lower bound, and is not changed (O2; the type system, Consequences).

A type is never path dependent. A type variable is one type, represented by a class (the type system, Equivalence classes), and solving makes each of a class's decisions once (O4). What differs along a path is only which parts of a value have been written (ownership §4).

A transparent type is a type whose elements the language knows: an object, an enum, `Error`, a tuple, an array, an `Option` and a `Result`. Every other type is opaque in its parts (the type system, Types).

The language knows the elements of such a type, and its shape is the language's own, so its meaning is its parts'. It has an impl of a generic function (extern fn §6) where the function's meaning at the type maps one to one onto its parts, every part has an impl of it, and that meaning relies on no law the parts' impls state. An enum, `Option` and `Result` hold one variant, so there the result's variant must follow from the value's: the function takes the type in exactly one parameter, and its result is that argument's variant. `clone` is such a function at every transparent type. Where the function's meaning at the type instead combines its parts' answers, by a combination the language defines, it has an impl only where every part's impl states a law (extern fn §3) that the combination keeps, and that impl states the law in turn. `eq` is such a function: a structure's equality is its parts' taken together, and equivalences taken together are an equivalence, so it has an impl of `eq` where every part's `eq` is declared an equivalence. Without the law it has none, since whether its equality would be partial or total cannot be known.

## 2. Where values meet

An object's fields, and an enum's variants, are ordered by their names' text, so the order is a fact of the type, the same wherever the type is written and known from the names alone; a variant's tag is its place in that order.

The values that meet within one transparency are a place and what is assigned to it, the branches of an `if` or a `match`, and a body's result and its tail, its `return`s and its `?` exits (the type system, Meetings), and they are unified into one class (O1). A class's head is decided once everything that enters it (the type system, O3) has given its head, as the least head that every position's head and every lower bound reaches by coercion (§3), and the parts of the positions' heads are unified with the class's parts (O6). Where values meet, only coercion changes a value: two values whose nodes no coercion relates are refused there, even where a conversion goes between them (O10; the type system, Consequences). Enums of two names have two constructors (the type system, Types), and no coercion relates them. `Option` and `Result` are primitive types, closed like an extern enum; a variant is written with its enum's name, except their `Some`, `None`, `Ok` and `Err`. `Error` is a keyword, the language's enum, and its variants are made only by `?` (O25).

A function value's members are its closures. A lambda expression gives a function value whose one member is the closure of that lambda (O29), and a function value coerces to one with more closures (§3), so where function values meet, the head of their class has the closures of each. Where function values, or values of one function type, meet, their effects and their flows join, which form lattices: the joined function is once where either is (functions §3), and may be split only where both sides may, at one cost (effects §6), so a joined function is never assumed to do less than either side. Declared facts (extern fn §3) do not join, and a joined function carries none.

## 3. Coercion and brand types

A change is what a value undergoes where it passes a position, made of coercions and conversions; the change made of none is the empty change. A coercion is a change the language gives: `&mut T → &T`, which changes the mutability; `! → U`, which changes the node; an object to one with only some of its fields, and an enum, or an `Error`, to one with more variants, which change the members; `&[T; n] → &[T]` and `&mut [T; n] → &mut [T]`, which change the target's constructor; a function value to one with more closures, which changes the members; and a function value to a function type, which changes the node, the function type's parameters and result being unified with the parameter and result classes of each closure's instance (O30) (the type system, Changes). A conversion is a declared function `S → T` (§7). A coercion is made at every position of a body, where values meet and at a boundary (O10).

A change acts on the whole value at a position. It changes the value's node and members, and the type of no part it carries: each part of the value is one type with the corresponding part of what the value passes into (O9). An object coerced to one with only some of its fields holds each of them; the others end where it is coerced (ownership §6).

A brand type is a part of an extern-defined type, the name of a storage (ownership §6). A struct or a transparent type is not branded; only its parts may each be (the type system, Brand types). A type is branded by at most one brand type, and two different brand types are never made one (O28), so two types branded by different brand types are not one class (the type system, Consequences). Only the compiler makes a brand type. A declaration may brand its result by the brand type of a parameter, to one value or to several; it never brands one type by two brand types. A brand type in the result of a declaration or a body that no parameter's type is branded by is made anew, as a free class, at each use, in the scope the use lies in, and a brand type does not leave the scope it is made in: a program is refused where a class outside that scope would be branded by it (O28). A scope is the text of a body or a lambda, or one iteration of a loop, and scopes nest; a class belongs to the scope in whose text it is made, and two classes unified into one belong to the outer of their scopes (the type system, Brand types).

## 4. Bottom and references

`!` is the bottom type. No type is `!` by holding a part of type `!`. A structural constraint holds of `!` (O7). No value has type `!`, so an expression that gives no value decides nothing of its type: its class's head is decided from what enters the class, and what the class passes into gives it a head only at the fixpoint, as an occurrence (O3, O20); a class with no head whose records accept every type falls back to `!` (O21; §5).

No type has a reference directly as its target; the parts inside a target are not subject to this, the argument of `&N⟨&U⟩` for example. A lend `&ₘ p` gives a reference whose target is the place's value with no reference above it, and whose mutability is the least of `m` and the mutabilities of the references taken off (O23).

## 5. Defaults

Defaults apply only where nothing more can be decided. At the fixpoint, after occurrences (O17), a class with no head takes the one type its records accept with nothing to choose by: where its records accept the types of a LitVar's range, its family's default, `i32` for an integer and `f64` for a float, and where they accept every type, `!` (O21). Fallback is taken for every class of the fixpoint at once (O19), and solving returns to settling after it (O17). An effect nothing constrains is opaque, a function type's flows nothing decides state every flow (as a declaration's default does, extern fn §4), a function value's loans nothing decides are none and how often it may be called is many (functions §3). A variable a bound constrains and no use answers is refused.

## 6. Deciding by type

What a `for` iterates, what `?` unwraps, and which declaration a name or a method call reaches are decided by a type, wherever in the program that type becomes known. Solving only adds to a class's records, and makes each of its decisions once (O4); the outcome, and the position of every refusal, do not depend on the order in which settling takes its steps (O19). A program is refused at each position whose record its decisions do not satisfy, and at each position left undecided (O22). `!` says nothing of a type: a decision that reads it decides nothing from it and refuses nothing for it.

Which declaration a name or a method call reaches is decided as a use is. At each use, the signature its candidate writes, or the common part of its candidates (the type system, Common part), is made anew as classes with maximal sharing (O13). A use records the common part of its candidates before it is decided, and the rest of the candidate it is decided as once it is decided; until it is decided, the upper bound of each argument's boundary is the common part of the candidates' parameters (O14). A use is decided as the one candidate that what is decided of its arguments and its result reaches: each argument by a change to the candidate's parameter, and the result by equality to the candidate's result type (O15). A use's result is unified with the class of the result type its candidate writes, and no change is made there (O16).

A method call's receiver is its first argument. Its adjustment is the first of the receiver as written, its `&` and its `&mut` that reaches a candidate, each lend taken as far as the place allows (the type system, Adjustments), and each position records the adjustment its value takes where it passes (O24).

## 7. Conversions

A conversion is a declared function `S → T`, and an auto-conversion is a chain of conversions, `S → U → T` from the conversions `S → U` and `U → T` (the type system, Changes). An auto-conversion is made at a boundary alone, once, after the node of the boundary's class is decided (O10). No position of a body lies beyond a boundary, so the change at a boundary is one stage of coercion followed by one chain of conversions, and exactly one such change goes from the value's node to the upper bound's node (O11). The parameter of a conversion writes its node with distinct holes as the parts below the node; the signatures of the chosen conversions are made anew at the boundary, and their functions are called where the value passes (O12). Where not exactly one such change goes between the two nodes, the program is refused at the boundary (O22), and the refusal names the conversions that left it undecided. A qualified name reaches one declaration, so a conversion can always be decided by writing one.

## 8. Specialization

An extern-defined type whole and concrete, with no variable of any kind in it but its brand type, may carry `#`, the mark that it can always be specialized, at its root. It is written in a declaration's signature as any concrete type is, never over a type variable and never as an extern-defined type's argument: `Vec<#F<A>>`, `F<#A>`, and a marked tuple, object or enum are not types. Only an extern fn gives a value of `#F<A>`.

The mark is ordered, marked below unmarked, and joins as an effect does (§2): where a marked type and an unmarked one meet, the meeting is unmarked. A value an extern fn gives marked starts marked. Each use that takes it unmarked raises it: a declaration's type variable standing for it, an extern-defined type's argument included; an unmarked type it meets; a conversion from the unmarked type taken from it. A declaration's parameter written `#F<A>` fixes it marked, as `eq` fixes an effect, and a value raised past it does not enter there. The type system does not handle the mark (the type system, Types); the mark is known once no value can still meet in it, and a decision that reads it waits until then. So a value is unmarked from where it is given whenever any of its uses takes it so, the one change of its representation is there, and no mark is coerced anywhere else.

A declaration taking `#F<A>` is an overload beside one taking `F<A>`, reached as any overload is (§6), and means what that one means: the same function, specialized. A registry makes one by making the same function concrete at the marked type, which keeps that by construction; an author who writes one by hand keeps it (extern fn). A registry's pair differs only in marks, so it is one declaration whose positions of the named type share one mark, joined as any mark is: the call reaches it, and which of the two it is follows from that mark once known, marked where every use takes the values marked. A backend may hold a value of `#F<A>` in a representation of its own, and takes the unmarked one where a value is given unmarked. So a backend that treats `#F<A>` as `F<A>` throughout keeps every program's meaning.

Specialization at a type argument is rejected. It lets a generic type change its representation for one argument, as C++'s `vector<bool>` does: the specialized type is then no longer the generic one at that argument, a part of it can be lent only through a stand-in, and generic code meets a type that behaves otherwise. `#` specializes a whole type only. It is chosen where an extern fn gives it and kept only where every use takes it so, it is never a generic type's argument, a reference to it lends it whole, and its overloads mean what the unmarked ones mean, so the specialization changes a representation and never a meaning.
