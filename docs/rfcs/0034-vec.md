# RFC-0034: The dynamic-length sequence is `Vec<T>` on both sides

Status: Accepted
Date: 2026-09-16
Extends: RFC-0022, RFC-0027, RFC-0032

## Ruling

The language's dynamic-length sequence is named `Vec<T>`, and the Rust
value that crosses as one is `std::vec::Vec<T>` itself. There is no
newtype: `Vec<T>` implements `TyArg`, `Cross`, and `ExternTypeDecl` in
`acvus-extern`, next to `Arr<T, N>`, and a Rust struct that holds a
`Vec<T>` field declares an object whose field is a `Vec<T>` (RFC-0032).
The functions on it — `reverse`, the container and iterator instances,
and the demotion `std::vec` from an array (RFC-0027) — stay in
`acvus-ext`.

## Rationale

`List<T>` was a newtype over `Vec<T>` whose only work was to carry the
language's name; every function on it unwrapped it and every value built
for it wrapped it. A struct declared for the boundary would then have had
to name `List<T>` where the rest of its code says `Vec<T>`, so a wire
struct and its language object could not be one struct. Giving the
language the same name Rust uses removes the wrapper and the second
struct at once.

The declaration moves to `acvus-extern` because `Vec` and the three
traits are all foreign to `acvus-ext`: the orphan rule leaves only the
crate that owns the traits.

## Not built

- No rename of the MIR's array-literal instruction, `list [..]`: it
  builds an `Array<T, N>`, not a `Vec<T>`.
- Earlier RFCs keep the name `List` they were written with.

## Consequences

- `acvus-extern`: `impl TyArg / Cross / ExternTypeDecl for Vec<T>`,
  `vec_ty`.
- `acvus-ext`: `list.rs` is gone; `vec.rs` holds `std::vec`, `reverse`,
  and the registry; instances are named `*_vec`.
- Scripts: the type reads `Vec<T>`; the demotion reads `vec(..)`.
